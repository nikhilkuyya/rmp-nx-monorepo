## Design Pattern: Hybrid Module System

### Problem It Solves

**Root Cause:** Impedance mismatch between tool expectations and codebase conventions
- Knex CLI expects: CommonJS modules (`require`, `module.exports`)
- Project uses: TypeScript/ESM (`import`, `export`)
- Result: Runtime failures, unclear error messages, debugging friction

### Solution Structure

```
┌─────────────────────────────────────────┐
│         TypeScript/ESM App Code         │
│  (uses db from connection.ts)           │
└──────────────┬──────────────────────────┘
               │ requires()
┌──────────────▼──────────────────────────┐
│       knexfile.cjs (CommonJS)           │
│  ✓ What Knex CLI expects                │
│  ✓ Programmatic config (path.resolve)   │
│  ✓ Runtime execution                    │
└──────────────┬──────────────────────────┘
               │
┌──────────────▼──────────────────────────┐
│       knexfile.d.ts (Declarations)      │
│  ✓ What IDE type-checker expects        │
│  ✓ Autocomplete, inline docs            │
│  ✓ Zero runtime overhead                │
└─────────────────────────────────────────┘
```

### Why This Pattern Works

1. **Respects Tool Boundaries**
   - Knex CLI is a mature, stable tool with clear expectations
   - Rather than fight it, provide what it expects
   - Reduces friction for new team members familiar with Knex

2. **Maintains Developer Experience**
   - TypeScript devs still get full IDE support
   - No changes to app code (ESM/TypeScript stays)
   - Transparent to end users

3. **Minimal Complexity**
   - 3 files + 1 require statement
   - No transpilation, loaders, or wrappers
   - Straightforward to debug (what you see is what runs)

4. **Robustness via Absolute Paths**
   - `path.resolve(path.dirname(__filename), '...')` works from CI, Docker, monorepo, or local dev
   - Relative paths are fragile in CI/deployment contexts

2. **Database Observability**

   - Low overhead, high signal

3. **Asset Management Awareness**
   - Explicitly added `knexfile.cjs` to build outputs
   - Shows understanding that CLI tools need runtime file access
   - Prevents silent failures in CI/deployment

### ⚠️ Considerations for Maintenance

1. **Manual Type Declaration Sync**
   - `.d.ts` file is separate from `.cjs` implementation
   - If config shape changes, both files must update
   - For a low-churn config file, acceptable; document reminder in code

2. **TypeScript Strictness & `.cjs`**
   - The `.cjs` file won't be type-checked by TypeScript compiler
   - Migration files use mixed syntax (`module.exports` + `: Knex` type annotation)
   - Consider documenting this hybrid syntax in contribution guidelines

3. **Build Output Verification**
   - Must ensure `knexfile.cjs` is included in final build
   - Add to deployment documentation and CI checks
   - Consider a startup validation: attempt `knex migrate:list` to verify config loads
